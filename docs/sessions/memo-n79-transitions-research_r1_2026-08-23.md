# Transitions research: drawer and destination switch

## Part 1: What the tree does today

**Svelte version:** `apps/web/package.json`: `"svelte": "^5.50.1"`, `"@sveltejs/kit": "^2.50.2"`.

**No Svelte transition directives exist anywhere in `src`.** A repo-wide grep for `transition:`, `in:`, `out:`, `animate:`, `flip`, `crossfade` found zero directive usages (only false positives: the CSS `transition` property, and unrelated words like "origin", "sustain"). Every animation in the tree is hand-built: CSS `transition` on a property, or a `@keyframes` animation toggled by a class the component computes in script.

**No View Transitions API usage.** Grep for `view-transition`, `startViewTransition` across `src`: no matches.

**No `will-change`, `contain`, or `content-visibility` anywhere in `src`.**

**`ssr = false`**, `src/routes/+layout.ts:3`.

**The drawer, desktop:** `Drawer.svelte:694`, `.drawer { transition: width 1500ms cubic-bezier(0.22, 1, 0.36, 1); }`, and `.drawer.collapsed { width: 0px; }` (`Drawer.svelte:729`). Width is also set inline per frame of state: `Drawer.svelte:299`, `style="... {isMobile ? '' : \`width: ${collapsed ? 0 : width}px\`}"`. This is a **layout property** (reflow), animated for **1500ms**.

**The drawer, phone (`max-width: 767px`):** the drawer is explicitly **not** a bottom sheet. `Drawer.svelte:1482` starts a media block whose comment (`:1477-1481`) records "Dann's ruling, 2026-08-19: the desktop's illusion is horizontal motion, the phone's vertical motion was a form-factor concession, and the concession is withdrawn." On phone the drawer becomes `position: fixed`, a full-screen-minus-lip overlay (`Drawer.svelte:1499-1509`), and `.drawer { transition: transform 400ms cubic-bezier(0.22, 1, 0.36, 1) !important; }` (`:1514`); collapsed state is `transform: translateX(-100%)` (`:1529-1531`). This **is** compositor-only (`transform` + implicit `filter: none` override at `:1499`, dropping the drop-shadow filter specifically because "filter... rasterizes on every frame of the 400ms slide," per the comment at `:1495-1497`).

So: desktop pays a 1500ms layout-property animation; phone pays a 400ms transform-only animation. They are not the same mechanism, contrary to the premise that the drawer is a bottom sheet on a phone — it is a left-arriving full-screen overlay there.

**Destination/tab switching:** `Destination` is actually **three** values (`studio | learn | guide`), not four; Studio holds two documents (`transcription | shane`) — `src/lib/destinations.ts:27-38`. The four-way `TabId` is a wire/display concept only (`HeaderBar` hues, `DeskHead` labels).

Switching is **not** routing and **not** a `{#key}` block. `src/routes/+page.svelte`'s `handleTabChange` (`:1640-1659`) computes a direction (`tab-enter-from-right` / `-left`) from `TAB_ORDER` index comparison, sets `surfaceFor(tab)` on `destination`/`studioDocument` (plain `$state` reassignment), applies the class string to `.main-content` (`:2268`), and clears it after 200ms via `setTimeout`. The same class also lands on `.drawer-content` in `Drawer.svelte` via the `tabTransitionClass` prop (`:329`). Both are driven by one CSS `@keyframes` pair: `Drawer.svelte:934-957`, `tabSlideFromRight`/`tabSlideFromLeft`, `opacity` + `translateX(12px)→0`, **175ms**, `cubic-bezier(0.25, 0, 0.15, 1)` — compositor-only properties.

The paper does **not** remount on a destination switch: `<main class="main-content ...">` is one persistent element; content inside swaps via `{#if destination === 'studio' && studioDocument === 'transcription'} ... {:else if destination === 'studio'} ... {:else if destination === 'learn'} ...` (`+page.svelte:2279, 2329, 2358` approx) — conditional rendering, no keyed block on the destination itself.

A separate, narrower keyed block exists: `{#key doc.id}` around `<ScoreUploader>` only (`+page.svelte:2067`), remounting the uploader when the open song changes — unrelated to destination switching, but see Part 4.

A second small animation, `breath-in`/`breath-out` (`+page.svelte:2977-2991`), fires on `paperBreathClass` for "moments of meaning" (e.g. a transcription trigger, `:471-477`) — `opacity` + `translateY(2px)`, 150-250ms, also compositor-only, also class-toggled rather than a directive.

**Reduced motion is already handled, per-component, by hand** (not via Svelte's `prefersReducedMotion`): `Drawer.svelte:1633-1651` zeroes the width transition, chevron transition, tab-enter animations, and TOC-grid transition; `+page.svelte:2991-3001` zeroes `breath-in`/`breath-out` and `.main-content`'s tab-enter animations; `InspectorPanel.svelte` and `Pacifier.svelte` carry their own `@media (prefers-reduced-motion: reduce)` blocks too.

## Part 2: What Svelte 5 provides

- **`transition:`/`in:`/`out:`** (https://svelte.dev/docs/svelte/transition): bidirectional, reversible mid-flight. Built-ins live in `svelte/transition` (https://svelte.dev/docs/svelte/svelte-transition): `fade` (opacity), `fly` (x/y transform + opacity), `slide` (axis-based, animates the layout height/width, not transform), `scale` (transform scale + opacity), `blur` (CSS `filter`), `draw` (SVG stroke, needs `getTotalLength()`), `crossfade` (paired send/receive, position-to-position transform). Local (default) fires only on that block's own mount/unmount; **`|global`** makes it fire when an ancestor block's condition changes.
- **Execution model:** Svelte's docs state a preference for `css`-returning transition functions over `tick`-based ones "since web animations execute off the main thread" (Web Animations API), and the built-ins are implemented this way. A custom transition using `tick` runs on the main thread every frame, which competes with JS work; a custom transition returning a `css` string is handed to the WAAPI and can run off-thread when it only touches `transform`/`opacity`/`filter`. `slide`, because it animates `height`/`width` directly (a layout property), forces a reflow every frame **regardless of `css` vs `tick`** — the off-main-thread benefit does not exempt layout properties from repaint/reflow cost.
- **`animate:flip`** (https://svelte.dev/docs/svelte/svelte-animate): FLIP-technique reposition of siblings in a keyed `{#each}`, computed in JS (measures start/end, inverts, plays), can hand off to `css` or `tick`.
- **`prefersReducedMotion`** (https://svelte.dev/docs/svelte/svelte-motion), since Svelte 5.7.0: a reactive `MediaQuery` object (`prefersReducedMotion.current`) meant to be read inside a `transition:` parameter (e.g. `transition:fly={{ y: prefersReducedMotion.current ? 0 : 200 }}`). The docs flag that the OS-level `@media (prefers-reduced-motion)` CSS query does **not** automatically suppress `transition:`/`in:`/`out:`/`animate:` directives — those need this explicit check, unlike the hand-written CSS this codebase already uses, which the plain `@media` query does cover.
- **View Transitions API + `$effect`:** SvelteKit's own writeup (https://svelte.dev/blog/view-transitions) wires `document.startViewTransition` through the `onNavigate` lifecycle hook in `+layout.svelte`, for **route** navigations. Ilya's destination switch is not a route change (single route, `ssr = false`, state held in one `+page.svelte`) — `onNavigate` would not fire for it. Reaching for the View Transitions API here would mean calling `document.startViewTransition(() => { /* the $state mutation */ })` by hand at the call site (e.g. inside `handleTabChange`), not through SvelteKit's navigation hook. That blog post also says browser support was "currently only Chrome" at time of writing, which is now stale.
- **View Transitions API browser support, today:** WebKit added the same-document View Transitions API in **Safari 18** (https://webkit.org/blog/15865/webkit-features-in-safari-18-0/, "WebKit added support for the View Transitions API in Safari 18"), i.e. iOS 18, released September 2024 — roughly two years old as of today. MDN marks the API "Baseline 2025 — newly available" as of October 2025 (https://developer.mozilla.org/en-US/docs/Web/API/Document/startViewTransition), which covers the cross-document (MPA) variant; the same-document variant Ilya would use has been in Safari since 18.0. Per spec, browsers skip the visual transition and swap DOM directly when `prefers-reduced-motion: reduce` is set, unless the page overrides that in CSS — not established from the docs fetched whether that default-skip behaviour needs any opt-in code from Ilya's side.
- **Cost model relevant to a 2019 iPhone** (from the docs above, not independently benchmarked here): `transform` and `opacity` (and, with caveats, `filter`) are compositor-only — no layout, no repaint of surrounding content, cheapest. `width`, `height`, `top`/`left` (not `transform`) force layout (reflow) on every frame, which is what `slide` and Ilya's own `.drawer { transition: width }` do today.

## Part 3: Options, weighed

**Drawer opening/closing**

1. **Leave as is.** Desktop: 1500ms `width` transition, a layout property, reflowing the paper and drawer siblings every frame for a second and a half. Phone: 400ms `transform: translateX`, compositor-only, already cheap. Cost: the desktop path is the expensive one in this whole tree — the only multi-hundred-ms layout-property animation found. No reduced-motion cost since it's already handled (`:1633-1637`).
2. **Move desktop to `transform` (translateX or scaleX) with `width: 0` set only via inline style pre/post transition, no transitioning `width` itself.** Singer sees: the same slide, visually. Mechanism: CSS `transition: transform`, no Svelte directive needed — same pattern already proven on phone. Properties animated: `transform` only, compositor-only. Cost: eliminates the reflow entirely; the paper beside it would still need `.drawer-clip`'s `overflow: hidden` to avoid a scrollbar flash, and the drawer's own inline `width` (which controls the paper's actual layout width) would need to jump at start/end rather than tween — this changes the "paper widens as the drawer closes" feel the current `width` transition gives, to a "drawer slides then paper snaps." Duration/easing: keep 1500ms curve or shorten (see below). Reduced-motion: `transition: none`, same as today.
3. **`transition:slide` (Svelte built-in) on the drawer body.** Singer sees: comparable to current desktop behaviour. Mechanism: Svelte directive replacing hand-written CSS. Properties animated: `slide` still animates height/width (a layout property, per Part 2) — this does **not** solve the reflow cost, it only moves the same cost into a directive, and adds the `|global` question (the drawer's box is not conditionally rendered — it always exists, only collapses — so `transition:slide` may not even be the right primitive; it targets mount/unmount, not a state toggle. This option needs the drawer's collapse to become an `{#if}` block, which conflicts with the mic-capture concern in Part 4). Cost: same reflow as today, plus new directive-vs-CSS complexity, likely a step backward on cost with no clear gain.

**Destination switch (the four-way `TabId`, i.e. within Studio and across Studio/Learn/Guide)**

1. **Leave as is.** 175ms `opacity`+`translateX(12px)` `@keyframes`, class-toggled, compositor-only, on both `.main-content` and `.drawer-content`. Cost: already cheap; already reduced-motion guarded (`+page.svelte:2991-3001`, `Drawer.svelte:1642-1644`).
2. **Replace the hand-rolled class toggle with `transition:fly`/`in:fly` + `out:fly` on the swapped content.** Singer sees: same slide-fade, possibly reversible mid-switch (a rapid double-tap would look smoother — genuinely bidirectional). Mechanism: Svelte directive; since the destinations are `{#if}`/`{:else if}` branches already, this is a natural fit, with `|global` needed if the transition should span a `{#key}` or nested conditional rather than the outermost block. Properties: same `x`/`opacity`, compositor-only. Cost: near-identical to today's; the win is bidirectionality and less hand-rolled state (`tabTransitionClass`, the `setTimeout(200)` cleanup) rather than a performance change. Trade-off: this is where the `{#key doc.id}` precedent (Part 4) matters — a careless keyed wrapper around the whole switch would remount `ScoreUploader`/`CalibrationWizard` and could interrupt calibration or an in-progress upload.
3. **`document.startViewTransition()` wrapping the `surfaceFor(tab)` state assignment, called directly in `handleTabChange`, guarded by feature-detection and `prefersReducedMotion`.** Singer sees: a native cross-fade/morph the browser computes from before/after screenshots, potentially nicer default transitions with no bespoke `@keyframes`. Mechanism: not a SvelteKit `onNavigate` hook (no route change here) — a manual call at the click handler, `$effect` not required since the trigger is the same event that currently sets `tabTransitionClass`. Properties: browser-internal (pseudo-element cross-fade), not directly one of `transform`/`opacity` but implemented via compositor layers. Cost: supported on iOS Safari since 18.0 (about two years, solid by today); each call snapshots the old and new visual state, which is heavier per-switch than a plain CSS animation, and any promise passed to it that resolves slowly stalls the switch visually (noted in Svelte's own writeup) — worth measuring against the 2019-iPhone (A13, iOS 18-capable) budget rather than assuming it is free. Reduced-motion: needs an explicit skip (call the state change directly, bypass `startViewTransition`) since the CSS media query alone does not gate the JS API call.

## Part 4: The traps

- **The drawer body hosts a live microphone capture surface via `display:none` toggling, not remount.** `+page.svelte:2008-2011` passes `<CalibrationWizard>` into `<Drawer>` as the `voiceTakeover` snippet; the drawer's own `.stowed { display: none; }` comment (`Drawer.svelte:927-930`) states explicitly: "A stowed region keeps its component tree and its state... which is the whole reason the wizard can be entered, left, and re-entered without losing a captured vowel." Any transition mechanism for the drawer that remounts its content (a keyed block, a Svelte `transition:` requiring an `{#if}`) risks tearing down the mic/AudioContext mid-capture. `CalibrationWizard.svelte:1844-1845` separately notes its readiness meter deliberately carries **no** CSS transition because "the width is driven per frame from one clock, so a transition would add a second, slower clock that disagrees with it" — a precedent against layering CSS transitions onto anything already animated by a live audio clock.
- **`ssr = false`** (`+layout.ts:3`): the whole app renders client-side only; there is no server-rendered first paint to protect from a transition flashing on load, but it also means any `onNavigate`/hydration-timed transition trick common in SvelteKit examples doesn't map cleanly onto Ilya's single-route shape.
- **The paper is also the print surface.** `Paper.svelte:58` injects a `@page` print stylesheet inline. Not established from the tree whether any candidate transition (opacity/transform on `.main-content` or its children) would be visible in a print preview or bleed into `@media print`; worth an explicit `@media print { animation: none; transition: none; }` guard given the existing `@media (prefers-reduced-motion: reduce)` pattern already used throughout.
- **No `{#key}` wraps the destination switch itself** (good — nothing there would replay on every state change), but `{#key doc.id}` around `<ScoreUploader>` (`+page.svelte:2067`) is a real keyed block nearby; a future `transition:`/`animate:` added carelessly at a shared ancestor could catch it and replay on song changes unrelated to navigation.
- **`docs/memory/ENVIRONMENT.md`** flags, on grep for `hover`/`transform`/`drawer`:
  - `:1593-1602`, "`.drawer-lip:hover` LATCHES ON iOS, AND NOTHING IN `Drawer.svelte` IS HOVER-GUARDED" — a tap latches `:hover` until the next touch elsewhere; any transition keyed off `:hover` on the drawer lip/handle will misfire on iOS the same way this existing background-colour rule does.
  - `:1614-1616`, "A chevron's transform read in the same call that clicks it returns the PRE-TRANSITION value... Wait for the transition before reading a transform" — a documented instrument fault: JS that reads a CSS-transitioned property (`getComputedStyle`, a bounding rect) immediately after triggering the transition gets the stale value. Relevant to any orchestration code (e.g. sequencing a View Transition with a manual layout read) added around these transitions.
  - `:1273-1284`, "A 'NOTHING MOVES IN THE DRAWER' TEST CANNOT BE RUN ON A PHONE" — on phone the drawer covers the whole screen, so comparing drawer motion across a state flip needs `.drawer-content`'s `scrollHeight` captured either side rather than a visual A/B; relevant to how any new drawer-transition work would be verified on-device.

## What I could not establish

- Whether `document.startViewTransition`, called directly (not via SvelteKit's `onNavigate`), incurs a measurable frame-budget cost on a 2019 iPhone (A13) specifically — no benchmark was run or found; only that the API is supported there.
- Whether the browser's default "skip the transition, just swap DOM" behaviour under `prefers-reduced-motion: reduce` applies automatically to a manually-invoked `document.startViewTransition()` call, or needs an explicit CSS override in this app.
- Whether any transition/animation would visibly affect or bleed into the `@page` print stylesheet injected by `Paper.svelte:58` — not tested.
- Exact frame timing/jank measurements for the current 1500ms desktop drawer `width` transition on real hardware — this memo reports the mechanism (a layout property) and its known cost category, not a measured frame rate.
