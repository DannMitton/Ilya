## 1. What the font carries

MEASURED, against `apps/web/static/fonts/finale-maestro/FinaleMaestro.json` and
against the `cmap` table of `FinaleMaestro.otf` itself, because a glyph name in
the metadata is not proof the face draws it.

| glyph | in Maestro's metadata | in Maestro's `cmap` | in Bravura's metadata |
|---|---|---|---|
| `restHBar` U+E4EE | yes, 4.208 × 2.056 sp | yes, glyph 994 | yes, 3.128 sp wide |
| `restHBarLeft` U+E4EF | yes, 2.692 × 2.056 sp | yes, glyph 995 | yes |
| `restHBarMiddle` U+E4F0 | yes, 2.216 × 0.72 sp | yes, glyph 996 | yes, 0.8 sp thick |
| `restHBarRight` U+E4F1 | yes, 2.692 × 2.056 sp | yes, glyph 997 | yes |
| `timeSig0` to `timeSig9` U+E080 to U+E089 | yes | yes, glyphs 111 to 120 | yes |

Finale Maestro 2.7 carries 2,728 glyph bounding boxes, and all four H-bar
glyphs are among them. So is the whole time-signature digit set, which is what
SMuFL supplies for a multibar rest's numeral and what the count is set in here.
Both faces the project ships carry all four, so the Bravura fallback path in
`smufl-metadata.ts` never has to invent a metric.

**The `Large` digits exist and I did not use them.** Maestro's 339 optional
glyphs include `timeSig0Large` to `timeSig9Large` at `U+F440` and up. They are
a font-specific Private Use assignment rather than a SMuFL registry codepoint,
so reaching for them would put a Maestro-only address into a module that has to
work on Bravura too. §3 offers numeral size as a scale on the standard digits
instead, which gets the same range of sizes from one codepoint.

**What this settles.** The bar's thickness and the proportion of its terminal
serifs are the face's, not this desk's. Looked at at forty pixels to the
stave-space: `restHBarMiddle` is a plain rectangle 0.72 spaces thick, and the
Left and Right terminals carry serifs reaching exactly one stave-space above
and below the middle line, which is to say from the second staff line to the
fourth. Nothing about the mark's weight is invented here.

## 3. The geometry, and where each number comes from

`TACET_REST`, at [staff-renderer.ts:317](../../packages/score-parser/src/staff-renderer.ts).

| number | shipped value | source |
|---|---|---|
| `measureSp` | 12 stave-spaces | convention, chosen at the browser |
| `barInsetSp` | 1.25 stave-spaces | convention |
| `numeralClearanceSp` | 0.9 stave-spaces | convention |
| `numeralScale` | 1, the size of a time signature | convention, on SMuFL's own digits |
| bar thickness | 0.72 stave-spaces | **the face**, `restHBarMiddle`'s box |
| serif reach | ±1 stave-space from the middle line | **the face**, the terminals' boxes |

`measureSp` is the width one consolidated tacet measure occupies, barline to
barline, before the system justifies. It is fixed for every run length, so a
run of 2 and a run of 30 take the same room and differ only in the numeral.
That is standard practice, and it is a decision rather than a finding: I have
no source that says a longer rest earns more width, so I did not graduate it.

I chose 12 against the engraved Without Sun song 1, where a sung 12/8 bar runs
about 20 stave-spaces. At 12 the tacet bar reads as a bar the singer counts
rather than as a gap between two of them.

**One thing the drawing will show you that prose will not.** Every system
justifies to the 672 px line, so `measureSp` sets the tacet bar's SHARE of the
line rather than its absolute width. On the engraved song the one tacet measure
comes out 97 px wide against a sung bar's 227 px. Changing 12 to 8 or to 16
moves that share, and the drawing's section A shows all three at true size.

### How the mark is drawn

The measure's extent comes from its BARLINES, not from the column's advance, so
the mark stays centred in its bar after the system stretches. The left bound is
the run's own opening barline, or the end of the key signature where the run
opens the system and there is no barline to open it. The right bound is the
next column's barline, or the system's closing barline where the run ends the
system.

Inside that, the bar is the face's Left terminal, the face's Middle glyph
stretched horizontally to the span, and the face's Right terminal.
**Stretched rather than tiled, and rather than filled with a rectangle of my
own.** Tiling the middle glyph opens a hairline seam wherever the advance
rounds. A rectangle of my own thickness disagrees with the terminals by
whatever the face's stub is not, and my first attempt did exactly that: at
thirteen times the join showed a step of about 0.12 stave-spaces. The middle
glyph is a plain bar, so a horizontal scale distorts nothing and its thickness
cannot disagree with the terminals it meets. Looked at again at thirteen times
after the change: the top edge runs flat from terminal to terminal.

### The single silent measure

**A whole-measure rest, no numeral.** Consolidation starts at two. A numeral
over one bar would be counting to one, and the whole rest hanging under the
second line from the top is what every publisher prints for a bar of silence.
This is convention and not Gould, like everything else in this section, but it
is convention with no dissenting practice I know of, so I built it rather than
bringing you a choice. Section D of the drawing shows 1, 2 and 23 bars side by
side if you want to overrule it.

## 6. `data-tacet` carries the score's scale, and this was a defect I caught

The group is `<g data-tacet="4-8" data-tacet-count="5">`. The range is in the
SCORE's measure indices.

It was not, at first. `sliceScore` rebases each slice's measure indices to
start at 0, so the renderer's first draft printed the slice's scale: a run at
score indices 4 to 8 came out `data-tacet="1-5"`, and a run in a later system
came out `0-0` for measure 13. Two runs in one document both claiming to start
at measure 0.

That is exactly the second scale §26 was worried about, and it would have been
real. `data-system` carries original indices and every event id carries the
original measure index because the parser mints it, so a new attribute in a
different scale would have been the only liar on the page.
`StaffRenderOptions.measureOffset` hands the offset back, `paginateScore` sets
it per slice, and a test pins it.

## 7. The correction surface: what it does now, proposed rather than decided

**A tacet run is not an entry, and nothing here makes it one.** Everything
below is measured on a hand-built score whose vocal part is silent for five
bars.

### The stepper

**It crosses the whole run in one press.** Selected on the last entry of m. 4,
one press of the right arrow put the loupe on m. 10. Measures 5 through 9 are
not visited, because `stepCursor` walks the drawn line and the run is not in
it. The loupe never rests on a tacet bar.

### The tap band

**The two neighbouring notes' hit rectangles meet inside the mark.** Measured
in client pixels on the desk: the mark spans 945 to 1033; the last note of the
bar before it owns 893 to 981; the first note of the bar after owns 981 to
1075. So a tap on the mark's left 41 percent takes the previous bar's last
note, and a tap on its right 59 percent takes the next bar's first note.
Nothing dies, and nothing selects the run.

Two things follow from that and are worth your eye. Those two hit rectangles
are 87 and 94 px wide against a normal 35, because the run stretched them. And
the mark itself is hit-testable but always loses, because the tacet pass paints
before the note loop and the hit rectangles paint after it. Confirmed by
hit-testing five points across the mark: every one resolved to a note.

The vertical band is untouched. §18's 2.5 spaces on a fine pointer and 7 on a
coarse one are about how far above and below the staff a tap is accepted, and
N.104 changes nothing there. The hit rectangles carry the same SVG user-space
`x` and `width` at 1400×900, at 430×932 and at 932×430, so the horizontal split
measured on the desk is the phone's too, by construction.

### The readout

**It says nothing about a tacet run, because it never holds one.**
`heldMeasureIndex` at `+page.svelte:1091` comes from a selected entry or from a
gap's anchor, and a tacet run has neither.

### What I would propose, for you to rule

1. **A tap on the mark takes the mark**, and the loupe holds the run: the tag
   reads its measures, the readout names it as bars of silence, and the verbs
   are all disabled because there is nothing there to alter. This is the most
   work and the most honest surface. It needs a readout string and probably a
   tag form, so it needs §8's table filled in.
2. **A tap on the mark does nothing**, and the two neighbouring hit rectangles
   are bounded at the run's barlines instead of meeting inside it. This is
   small, it removes the surprise of a tap on a rest selecting a note two bars
   away, and it coins no strings. It also leaves a dead stripe on the page,
   which N.71 spent a whole fix removing from the noteheads.
3. **Leave it exactly as measured.** A tap resolves to the nearer neighbour,
   the stepper hops the run, and the run is engraving only. This is what is
   built, it coins nothing, and it is defensible: the singer's business is with
   the notes, and the rest is there to be counted rather than corrected.

I have not chosen. My own lean is 3 now and 1 later, if real use asks for it.

### One thing I saw and did not chase

Loading a new score while the loupe is up leaves the loupe showing the OLD
document, magnified, until it is dismissed. I found it because the stale frame
still held a tacet mark from the previous score after the Lamm read had
replaced it. **This is not N.104's**: the loupe retains its whole last frame,
clef and notes and all, and the tacet mark was only the evidence that made it
legible. Worth a look, on its own number.

## 8. Strings

**No new user-facing strings, so no French table.**

I expected to need one, and the brief expected it too. What I found when I went
to write it: **nothing inside the notation SVG carries an accessible name
today.** The score region carries `T('profile.scoreRegionAria')` and each page
carries `T('profile.scorePageAria')`, both at `VoiceProfilePane.svelte:1006`
and `:1017`, and inside them no note, rest, clef, key signature or barline is
named. Giving the multibar rest a name alone would make it the only spoken
glyph on a page of silent ones, and it would put user copy into
`packages/score-parser`, a pure module that today ships none.

So the mark carries machine attributes and no copy: `data-tacet` and
`data-tacet-count`, in the same register as `data-system`, `data-hit` and
`data-analysis`. If you rule proposal 1 in §7, the readout will need a phrase
and I will bring the table then, English and French, coined marked against
adopted, before anything ships. **I coined no French here.**
