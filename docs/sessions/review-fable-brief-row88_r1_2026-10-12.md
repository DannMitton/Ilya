## The questions the desk asked

**Does the processor resize a wide line to 384 by 384 and destroy it?** Yes to the resize: `do_resize: true`, `size: {height: 384, width: 384}`, `resample: 2` (fetched `preprocessor_config.json`). `ViTImageProcessor` resizes to that height and width without keeping the aspect ratio (Fable's knowledge, not verified against the installed `transformers`). TrOCR was trained on text lines resized the same way, so a line of ordinary aspect (around ten to one) is what it has seen (Fable's knowledge, not verified). An underlay row is one line of print across a whole system (`report:33`), at Ilya's raster scale (`review-fable-brief-row81_r1:` the row 81 review's own words on `rasterizePdf` at 400/72; the pixel widths of row 81's crops are NOT ESTABLISHED in the inputs), with wide gaps between syllables. Its aspect is far past anything a line model saw. So the whole-row form will produce something, and it will not be a fair reading of the model. It stays in the run as a control, not as the answer.

**What Code should do instead.** Cut each row into chunks of bounded aspect, read each chunk, and join the strings with a space, in x order. Two cutters are on offer:

- **By ink gaps (recommended).** Project the row's ink onto x, as `rows.py` projected onto y (`report:24`); a gap wider than a threshold is a cut; group consecutive pieces until the next piece would push the chunk past a maximum aspect (width over height). This uses nothing from Tesseract, so column (t) measures the model and its own segmenter. The syllable gaps in an underlay are wide, so the cuts will mostly fall between syllables.
- **By row 81's (c) word boxes** (`ocr/<L>-c.json`, page pixels, `report:44`). Quick, but it hands the model (c)'s localisation and (c)'s misses: `report:212` says some Russian syllables have no box or a box offset from the note. A syllable with no box is scored "nothing" against the model, which is (c)'s fault.

The brief's "overlapping halves" is the weakest of the three: halves of a system-wide row are still far too wide, and joining two overlapped strings needs a fuzzy merge that will itself make errors `step5.py` would charge to the model. Drop it.

**Can `step5.py` score a boxless string?** It aligns printed syllables to tokens by edit distance (`report:104`); boxes are not named as inputs to step 5, but the token source is not stated and `step5.py` is not in the inputs, so NOT ESTABLISHED. The safe path is to write the model's output in the same file shape row 81's step 2 wrote (`ocr/<L>-t.json`: a list of words with `text`, and the chunk's box as the word's box, confidence null) and run `step5.py` unchanged. If `step5.py` needs a field the model cannot give, Code changes it by the smallest named edit and says so. One tokenising rule matters: Tesseract gave a hyphen as its own token («Ди», «-», «тя», `report:76`). To be charged the same way, the model's string is split on whitespace, and a token holding a hyphen is split into the part before, the hyphen, and the part after.

**Output length.** `generation_config.json` caps `max_length` at 64 tokens with 4 beams. The decoder vocabulary is 50265 with a `merges.txt`, the size of RoBERTa's byte-level BPE (Fable's knowledge, not verified against the model's `tokenizer.json`). If so, a Cyrillic letter costs one to two tokens and a long row (T's rows run to twenty syllables, `report:29`, `:66`) can exceed 64 and be cut short without error. Code sets `max_new_tokens` well above that and reports the longest output and whether any output ended without the end token. Chunking makes this moot for the chunked form; the whole-row control still needs it.

**Fairness against (a), (b), (c).** Those columns were read whole-row at PSM 7 with Tesseract's own segmentation (`report:44`). Column (t) is the model plus a segmenter Code wrote. The table header names the segmenter, and the recommendation says what the segmenter cost (chunks that cut inside a syllable, counted by eye on a sample). The same alignment and the same normalising (`report:68`) apply to every column.
